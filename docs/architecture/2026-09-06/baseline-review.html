Top recommendation

Start with trust and test evidence.

Preserve the baseline and outstanding failed verify during pruning. Follow with unique lane names and proof of retry passes. Those changes stop successful verdicts from being built on missing evidence. Complete ordinal identity before enforcing exclusive claims for exact functions.

01
StrongP1Small to medium scope

Keep trust evidence when pruning runs

Four-run fixture: baseline 1 becomes baseline 4 after prune; failed verify 2 disappears.

Before

↓
Verify 2 fails
↓

↓

↓

After

Run history
↓
One trust decision
↓
Preserve baseline + refusal
↓
Prune other eligible runs
↓
Refusal still blocks coverage

Problem

Retention and baseline selection apply separate rules. Deleting an outstanding failed verify lets later coverage become trusted without a successful verify.

Change

Keep the selected baseline and outstanding refusal through the existing store module. Make retention use the same trust decision as verification.

Deletion test

Delete retention's independent trust assumptions. The existing transactional store remains valuable.

Reserve work atomically

Two SQLite connections selected the same free function, then both inserted a claim. Two open claims remained.

Problem

The CLI checks availability, inserts ownership and emits work as separate operations. A second process can take the same path between those steps.

Change

Move acquisition into a short transaction owned by the store. Emit only acquired work and continue to another candidate after a conflict.

Deletion test

Delete the caller-side check-then-insert protocol. One store transaction gives every process the same ownership rule.

Validation and limits

What ran

The complete unit suite ran against the reviewed checkout: 3,005 passed, 1 failed, 8 skipped in 120.26 seconds. Eighteen additional focused tests passed. Temporary probes exercised trust, claims, identity, reader behavior, cache identity, lane evidence, mutation preparation and deadlines.

The one failing unit test hardcodes the POSIX command true. It failed again alone on Windows. An isolated copy passed after replacing only that command with the current Python interpreter running pass. The repository test remains unchanged.

What this does not establish

The review did not run the full e2e suite, production coverage or verify, publish a release, or modify source code. Synthetic allocation figures are Python allocations under tracemalloc, not process RSS. Existing production performance and the full language-parser grammar were not benchmarked or exhaustively audited.

The review maps the entire project and follows high-risk caller paths. It does not claim line-by-line validation of all 434 tracked files. Scripts, raw observations, per-area reports and the decision log are in the evidence bundle.
