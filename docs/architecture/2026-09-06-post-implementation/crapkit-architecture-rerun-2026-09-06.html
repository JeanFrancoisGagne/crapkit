Make automatic artifact reuse account for test inputs

StrongReproduced defect

Before

↓

↓

↓
passing verify ledger entry

After

Measurement input changes or validity is unknown
↓

↓

↓

Automatic reuse treats source ownership as the complete set of measurement inputs. A changed tracked test input outside src disappears from the freshness check. Verify then records a passing result from old coverage and JUnit even though a fresh lane fails on the same tree.

Give the lane code ownership of measurement validity. Changed tests, runner configuration, commands, and other unproven repository inputs must prevent automatic reuse. Use a conservative check until narrower dependency evidence exists. Keep explicit reuse-artifacts as a deliberate request to consume an existing artifact.

One lane-level decision protects both coverage and verify, including future callers.

The module that creates and consumes artifacts also decides whether its previous measurement still applies.

A public fixture can compare automatic reuse with a fresh run after source, test, command, and configuration edits. Assert runner calls, verdict, and ledger content together.

Separate CLI processes can execute the same lane and overwrite each other's configured artifacts between execution and parsing. Path uniqueness within one config does not protect overlapping invocations. A successful run can persist another invocation's measurement and digest without a warning.

One ownership rule protects coverage, verify, automatic reuse, logs, and artifact stamps.

AN1 · in-process

Bind analysis cache records to the bytes actually parsed

StrongReproduced defect

Before

Read A and calculate digest A
↓
Parser reopens path and reads B
↓
Cache digest A with records from B

After

One source input
↓
Matching digest and parsed records
↓
Publish one consistent cache entry

The analysis cache hashes a source file before the parser opens it again. An edit or deletion between the reads stores later records under the earlier bytes' identity. The wrong answer survives cache serialization and a normal restoration of the original source.

Concentrate ownership of source bytes, their digest and their parsed records in the analysis operation. Never store records against a hash obtained from different bytes. Refuse or retry an interrupted source read, and invalidate caches that can already contain mismatched records. Keep current metric rules, path restamping and the settled-file fast path.

One correction covers every analyze_files caller and every supported reader.

Byte identity and parsing belong together in analyze.py; cache.py can retain its pure partition/update role.

The existing analyze_files interface is the seam. Add controlled edit and delete interleavings, persisted cache round trips, warm/cold equality and spawned-worker variants. Preserve the existing cross-reader and typed-cache fixtures.

Evidence, files and tradeoffs
  • observation: The controlled edit replay returns CCN2/end4 on a warm hit for current source whose independent analysis returns CCN1/end2. The deletion replay saves and reloads cache.json, restores the original source normally, then gets one cache hit with zero functions instead of one. No restored timestamps or source changes in the reviewed checkout.
  • inference: Editors, generators or another command can cause this interleaving. Its frequency on user repositories is not measured. Inventory, coverage, verify and rescore consume the affected cached records.
  • caller_flow: cli.scoring._build_inventory -> _analyzed_corpus -> analyze_files -> _hash_paths -> analyze_jobs -> analyze_one -> updated_cache -> save_cache; later load_cache repeats the wrong metrics.

Source locations

  • path: src/crapkit/cache.py; lines: 31-40
  • path: src/crapkit/cli/scoring.py; lines: 61-94

Deletion test. Remove the handoff that couples an earlier path read's identity to a later independent parse. This is a deeper existing module, not a new cache wrapper.

Cost and risk. Medium. Source ownership can affect worker memory and IPC, so compare reading in the worker with retaining input bytes before choosing. Existing cache fingerprints need invalidation. Do not change ANALYSIS_VERSION solely for this cache correction.

None. Neither ADR0001 nor ADR0002 governs source cache ownership.

Keep override publication and run retention under one owner

StrongReproduced defect

Before

↓
Prune sees no audit and deletes run
↓
Grant succeeds; public audit is empty

After

Override intent
↓
One store rule owns publication and retention
↓

Prune can delete a hook run while its override alert is in progress. The alert then succeeds, the store accepts an audit row for the deleted run, and the ratchet grants debt. The public override history shows no record. Protecting runs added after selection does not protect a run already selected while its audit is incomplete.

Make the store preserve the relationship between an override and its run throughout publication and pruning. Keep the alert outside database locks. Refuse a grant when its audit cannot remain attached to a surviving run, and make retention honor an override that is being completed.

Hook overrides, verify overrides, runs prune and overrides history share the same durable rule.

Keep SQLite relationship and retention decisions in the store; keep alert execution and committed file handling with their existing owners.
